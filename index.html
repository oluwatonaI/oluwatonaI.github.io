Incident Report Case Study

Featured

A coursework incident report written up as a full case study, mapped end to end against the NIST Cybersecurity Framework. Tap the case study to expand the complete write-up.

Summary: The company experienced a security event when all network services suddenly stopped responding. The cybersecurity team found the disruption was caused by a distributed denial-of-service (DDoS) attack through a flood of incoming ICMP packets. The team responded by blocking the attack and stopping all non-critical network services, so that critical network services could be restored.

NIST Cybersecurity Framework — function by function
Identify

A malicious actor or actors targeted the company with an ICMP flood attack. The entire internal network was affected. All critical network resources needed to be secured and restored to a functioning state.

Protect

The cybersecurity team implemented a new firewall rule to limit the rate of incoming ICMP packets and an IDS/IPS system to filter out some ICMP traffic based on suspicious characteristics.

Detect

The cybersecurity team configured source IP address verification on the firewall to check for spoofed IP addresses on incoming ICMP packets and implemented network monitoring software to detect abnormal traffic patterns.

Respond

For future security events, the cybersecurity team will isolate affected systems to prevent further disruption to the network. They will attempt to restore any critical systems and services that were disrupted by the event. Then, the team will analyze network logs to check for suspicious and abnormal activity. The team will also report all incidents to upper management and appropriate legal authorities, if applicable.

Recover

To recover from a DDoS attack by ICMP flooding, access to network services needs to be restored to a normal functioning state. In the future, external ICMP flood attacks can be blocked at the firewall. Then, all non-critical network services should be stopped to reduce internal network traffic. Next, critical network services should be restored first. Finally, once the flood of ICMP packets has timed out, all non-critical network systems and services can be brought back online.

Project description: As a security professional at a large organization, I investigated potential security issues involving login attempts and employee machines. Using SQL filters — AND, OR, NOT, and LIKE — I queried the log_in_attempts and employees tables to pull exactly the records each investigation needed. This project shows the six queries I ran and explains how each one works.

QUERY 1Retrieve after hours failed login attempts

SELECT * FROM log_in_attempts WHERE login_time > '18:00' AND success = 0;

This finds failed logins that happened after business hours. AND means both conditions must be true: login_time later than 18:00, and success equal to 0 (a failed login). Filtering on time and success together narrows the results to the suspicious after-hours failures worth investigating.

QUERY 2Retrieve login attempts on specific dates

SELECT * FROM log_in_attempts WHERE login_date = '2022-05-09' OR login_date = '2022-05-08';

This pulls all login attempts from 2022-05-09 — the day of the suspicious event — and the day before. OR returns a row when either condition is true, so both days come back in one result set. Both conditions are written out in full because SQL needs the column name on each side.

QUERY 3Retrieve login attempts outside of Mexico

SELECT * FROM log_in_attempts WHERE NOT country LIKE 'MEX%';

This returns login attempts from everywhere except Mexico. The country column stores Mexico two ways — 'MEX' and 'MEXICO' — so LIKE with the pattern 'MEX%', where % matches any characters after MEX, catches both. NOT flips the match and excludes every row starting with MEX.

QUERY 4Retrieve employees in Marketing — East building

SELECT * FROM employees WHERE department = 'Marketing' AND office LIKE 'East%';

This finds Marketing employees whose offices are in the East building (offices like East-170 or East-320), so their machines could be updated. AND requires both conditions: department must equal 'Marketing' and the office must start with 'East'. The 'East%' pattern catches every East office regardless of room number.

QUERY 5Retrieve employees in Finance or Sales

SELECT * FROM employees WHERE department = 'Finance' OR department = 'Sales';

This pulls employees from either the Finance or the Sales department for a different security update. OR returns a row when at least one condition is true. Both conditions are written out completely — department = … on each side — because SQL can't guess the column from just one side.

QUERY 6Retrieve all employees not in IT

SELECT * FROM employees WHERE NOT department = 'Information Technology';

This returns every employee except those in the Information Technology department, since IT already had this update. NOT negates the condition, so all rows where the department is anything other than 'Information Technology' come back.

Summary

Across these six queries, I used AND to combine conditions, OR to include multiple values, NOT to exclude data, and LIKE with % to match patterns in text. Filtering by dates and times focused the investigation on the after-hours and event-day windows that mattered, and pattern matching handled real-world values like 'MEX' versus 'MEXICO'. Together, these filters turned two large tables into precise, investigation-ready answers.

Coursework from the Google Cybersecurity Professional Certificate. A vulnerability assessment of a public database server, focused on its current access controls over a three-month assessment period, with risk analysis guided by NIST SP 800-30 Rev. 1.

System Description

The server hardware consists of a powerful CPU processor and 128GB of memory. It runs on the latest version of the Linux operating system and hosts a MySQL database management system. It is configured with a stable network connection using IPv4 addresses and interacts with other servers on the network. Security measures include SSL/TLS encrypted connections.

Scope

The scope of this vulnerability assessment relates to the current access controls of the system. The assessment covers a period of three months, from June to August. NIST SP 800-30 Rev. 1 is used to guide the risk analysis of the information system.

Purpose

The database is valuable because employees use it every day to pull data and find customers. It needs to be secure to keep out threat actors who may try to take over the database through malicious attempts. If it were disabled, employees would be unable to access the data, work would stop, and customers could not be served properly. This assessment identifies the vulnerabilities in the database, how it can be accessed, and how it can be protected.

Risk Assessment

Threat sourceThreat eventLSRisk
HackerObtain sensitive information via exfiltration236
CompetitorObtain sensitive information via exfiltration326
EmployeeAlter or delete critical information133

L = Likelihood, S = Severity, Risk = Likelihood × Severity. Each threat event is paired with a threat source that could realistically carry it out.

Approach

Risks considered the data storage and management methods of the business. The likelihood of a threat occurrence and the impact of these potential events were weighed against the risks to day-to-day operational needs. I chose these three threats because they are the most severe. They are the most severe because they can shut down the database and also expose customer PII. They matter to the business because integrity must be upheld.

Remediation Strategy

Implementation of authentication, authorization, and auditing mechanisms to ensure that only authorized users access the database server. This includes using strong passwords, role-based access controls, and multi-factor authentication to limit user privileges. Encryption of data in motion using TLS instead of SSL. IP allow-listing for corporate offices to prevent unauthorized access. Remote staff worldwide need private remote access, so only authorized accounts can reach the database and threat actors are kept out.

  • Authentication & authorization: strong passwords, role-based access controls, and multi-factor authentication to limit user privileges.
  • Auditing: authentication, authorization, and auditing mechanisms so only authorized users can access the database server.
  • Encryption in transit: TLS instead of SSL for data in motion.
  • Network access: IP allow-listing for corporate offices, plus private remote access for remote staff worldwide so only authorized accounts can reach the database.

Course activity from the Google Cybersecurity Professional Certificate. Working from an event log and an employee directory for a payroll incident, I identified who was behind a suspicious login and what access-control failures made it possible.

Finding

The event log user Legal\Administrator was matched — by IP address 152.207.255.255 and the exact time 8:29:57 AM on 10/03/2023 — to Robert Taylor Jr., a Legal attorney and contractor whose contract had ended on 12/27/2019.

Issues identified

  • His access was never revoked after his contract ended.
  • Everyone in the directory was listed with Admin authorization, regardless of role.

Recommendations

  • Revoke or deactivate access on the contract end date, with a set procedure for doing so and regular access audits.
  • Apply role-based access control and least privilege, so authorization matches each person’s actual role.
